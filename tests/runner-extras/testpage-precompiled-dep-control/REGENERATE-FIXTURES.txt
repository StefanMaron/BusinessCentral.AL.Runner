How .alpackages/*.app and .deps-bin/*.dll in this folder were produced
========================================================================

These two binary fixtures make "TPCD Precompiled Control Dep" (page 65601,
table 65600) load as a genuinely Tier-1 precompiled dependency
(DependencyLoader.LoadOne: <bucketRoot>/.deps-bin/<Publisher>_<Name>_<Version>.dll)
with NO AL source reachable at runtime -- the exact shape a real precompiled
MS/ISV .app has (e.g. Base Application page 700 "Error Messages", the field
report for issue #2088), without needing an external Base Application.

IMPORTANT: the dep's AL source must NEVER live inside this suite folder (or
any other runner-extras suite folder) -- a flat-bundle suite's compile step
scans *.al recursively under its own root, so source sitting next to these
fixtures would get swept into the MAIN app's own compile and silently defeat
the whole point of the test (the page would get a real _parsedPages entry
instead of exercising the SymbolReference.json fallback path). Keep the dep
source external (a scratch dir, NOT under tests/), regenerate there, then
copy only the two binary artifacts back here.

WHY THE .app NEEDS A REAL SymbolReference.json, NOT JUST src/*.al
-------------------------------------------------------------------
`al-runner --emit-app` (the tool report-precompiled-dep-metadata's fixtures
were produced with) writes NavxManifest.xml + src/*.al only -- no
SymbolReference.json. That is sufficient when the main app never references
the dependency's objects BY NAME (that sibling suite calls Report.SaveAs by
numeric id). This suite's main app DOES reference the dependency's table and
page by name (`Record "TPCD Dep Table"`, `TestPage "TPCD Dep Page"`), which
needs the AL compiler's OWN cross-app symbol resolution -- and that requires
a REAL SymbolReference.json inside the .app, the same shape a real compiled
BC package carries (verified against Base Application 28.1's own package:
NAVX header, NavxManifest.xml, SymbolReference.json, [Content_Types].xml --
the OPC content-types entry is required too, or the compiler's package
scanner reports AL1023 "package not valid" even with a well-formed
SymbolReference.json present). There is no existing al-runner subcommand that
emits this; the script below builds it directly.

Dep AL source (place in a scratch dir, e.g. /tmp/tpcd-dep/), for producing
the DLL half only -- table 65600 "TPCD Dep Table" (fields: ID Integer PK,
Message Text[100], "Additional Information" Text[100]) and page 65601
"TPCD Dep Page" (PageType = List, SourceTable = "TPCD Dep Table", two field
controls: `field(Description; Rec.Message)` -- name differs from the field
it binds to -- and `field("Additional Information"; Rec."Additional
Information")` -- name matches):

  table 65600 "TPCD Dep Table"
  {
      DataClassification = ToBeClassified;
      fields
      {
          field(1; ID; Integer) { }
          field(2; Message; Text[100]) { }
          field(3; "Additional Information"; Text[100]) { }
      }
      keys { key(PK; ID) { Clustered = true; } }
  }

  page 65601 "TPCD Dep Page"
  {
      PageType = List;
      SourceTable = "TPCD Dep Table";
      ApplicationArea = All;
      UsageCategory = Lists;

          {
              repeater(Group)

The control ids (65601001 / 65601002) are arbitrary but must be internally
consistent -- GetPageControlFieldMap keys its returned map by whatever "Id"
SymbolReference.json states for each control, the same as LiveNavTestPage
passes to GetField() when the main app's compiled TestPage accessor reads
that control (both read the SAME symbol file's stated ids; they do not need
to equal BC's real IdSpace.GetMemberId hash for this fixture to prove the
fix, since nothing here depends on the dependency's OWN compiled business
logic dispatching to a specific id).

WHY NOT A THIRD "GENUINELY UNRESOLVABLE" CONTROL, END-TO-END
--------------------------------------------------------------
BC's own AL compiler only emits a GetField(id) dispatch for a field control
whose SourceExpression it can already validate, at compile time, as a plain
Rec.Field against the SAME symbol data the runner reads -- a plain Rec.Field
control that fails that check could never have compiled into a real
dependency .app in the first place (real BC rejects it at publish time,
before a .app is ever produced), and a control bound to anything else
(a name absent from the table, a compound expression) compiles to different
generated code that never reaches LiveNavTestPage.GetField at all (verified
while authoring this fixture: adding a third control this way to page 65601
never printed a single GetField trace for it, regardless of ordering, ID, or
whether it was even really implemented in the compiled dependency DLL). The
negative direction of the fix -- that GetPageControlFieldMap's fallback does
NOT fabricate a binding for an unresolvable control -- is pinned directly
against the fixed method instead, in
AlRunner.Tests/RecordPatchesGetPageControlFieldMapDependencyTests.cs.

GREEN with it -- no --package-cache needed, fully hermetic):

  dotnet run --project AlRunner -c Release -- --bc-version 28.1 --strict \
      tests/runner-extras/testpage-precompiled-dep-control
